# Seed v0.1 — Implementation Plan

> **REQUIRED SUB-SKILL:** Use the executing-plans skill to implement this plan task-by-task.

**Goal:** Ship a working v0.1 of the Seed app — an Android APK that bundles a proot+Alpine runtime, hosts a Python orchestrator + two `pi` agents, and lets the user chat to grow a Flask web app shown in a WebView.

**Architecture:** Three layers (Android shell / embedded Linux runtime / web app). Backend code is the same in dev (run `python service.py` on host) and prod (run inside proot on device). Agent loop is `user → middle-man (read-only pi) → dispatch JSON → worker (full pi) → files → webview`. Yolo mode inside the runtime.

**Tech Stack:**
- Android: Kotlin 1.9+, Jetpack Compose, Gradle 8.x, minSdk 26, targetSdk 34, ABI arm64-v8a
- Backend: Python 3.11, FastAPI, uvicorn, pydantic, pyyaml
- Agent: `pi-coding-agent` (Node.js CLI) wrapped in Python `pty` module
- Web app: Flask 3, Jinja2, stdlib `sqlite3`
- Runtime: proot (statically linked), Alpine minirootfs (arm64), tmux, git
- Testing: pytest (Python), JUnit 5 + Espresso (Kotlin)

**Reference design:** [`docs/plans/2026-06-30-seed-app-design.md`](./2026-06-30-seed-app-design.md)

---

## Phasing strategy

The plan is broken into 11 phases. **Each phase is independently demoable and ends with a commit on `feat/v0.1-bootstrap`.** We stop and demo at the end of each phase, then continue. If we run out of time, we still have a working app at any phase boundary.

| Phase | Goal | Demo |
|---|---|---|
| **0** | Project skeleton + local backend + web app skeleton | `python service.py` → `/health` 200 OK, `/api/ping` 200 OK, web app shows "Hello" |
| **1** | Shell endpoint (PTY-backed command exec) | `curl -X POST /shell/exec -d '{"command":"echo hi"}'` → "hi\n" |
| **2** | pi runner (PTY wrapper, ANSI strip, tool filter) | Spawn a fake pi, stream its output via WebSocket |
| **3** | Middle-man + worker orchestration | Chat via WebSocket: "add a /todos route" → backend dispatches → worker edits `app.py` → `/todos` returns 200 |
| **4** | System prompts (middleman.md, worker.md) | End-to-end agent loop: user request → clarifying question → dispatch → worker builds → response |
| **5** | Android shell (4 screens, nav, WebView) | APK installs, 4 tabs render, WebView loads a placeholder |
| **6** | Android ↔ backend wiring (Retrofit, WebSocket) | Chat screen sends a message, shows the response; Shell screen runs `echo hi` |
| **7** | Runtime extraction (proot + rootfs + backend) | First-run extracts to `filesDir/linux/`, ~60s progress bar |
| **8** | Foreground service (keeps proot alive) | App can be backgrounded, backend stays up |
| **9** | First-run setup wizard | Cold-start to "Ready" in <90s, navigates to Chat |
| **10** | End-to-end polish + "add a habit tracker" scenario | Full demo: chat → build → view in App tab |

**Test cadence:** Every phase ends with all existing tests passing. New tests written before the code they cover. Coverage target: 70%+ for backend Python, smoke tests for Android (instrumented Espresso for one happy path per screen).

## Open risks to watch

(Risks from design doc §12, focused on what could derail the plan above)

1. **Phase 2 is fragile.** The pi runner depends on assumptions about pi's stdout format. If pi changes its protocol, we break. Mitigation: pin pi version, write a parser that handles common cases.
2. **Phase 4 requires real pi.** If pi's installation or invocation differs from our assumptions, we have rework. Mitigation: check `pi --help` in Task 4.3 before writing the prompts.
3. **Phase 7 is heavy.** ~150 MB of assets committed to the repo. Mitigation: ignore from git, or use git LFS. (Currently: assets in `app/src/main/assets/linux/` are committed; this is OK for v0.1 since the project is small. We can revisit if the repo gets large.)
4. **Phase 8 depends on Android not killing us.** Use `startForeground` with the right type. Add a "why is this notification here?" explanation in the app's About screen.
5. **Phase 10 is open-ended.** Polish can take forever. Set a hard stop: "demo must work end-to-end by end of day 1, everything else is v0.1.1."

## Execution notes

- **Commit cadence:** 1 commit per task minimum, more if a task grows. Use Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`).
- **TDD discipline:** Write the test first, see it fail, write the code, see it pass, commit. Don't skip. If a task is hard to test (e.g., extraction), write the most useful test you can and document why it's incomplete.
- **Stop at phase boundaries.** Don't bleed into the next phase. Demo, then continue.
- **Update the design doc** if we discover the architecture is wrong. Don't silently change the plan.
- **When in doubt, simplify.** The user (you) can always add features later. Removing them is much harder.
